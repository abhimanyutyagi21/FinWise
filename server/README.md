# FinWise API

Node + Express + PostgreSQL. Email/password accounts, one workspace per user, and an AI proxy (Groq and Gemini).

## Database: Neon PostgreSQL

1. Create a project at [neon.com](https://neon.com) (any region close to your server).
2. In the project, open **Connect** and copy two connection strings for the same database:
   - **Pooled** (turn "Connection pooling" on; the host contains `-pooler`) goes in `DATABASE_URL`. The app uses it at runtime.
   - **Direct** (pooling off, no `-pooler`) goes in `DATABASE_URL_UNPOOLED`. Only migrations use it, because Neon's pooler runs in transaction mode and schema changes should use a normal connection.
3. Put both in `server/.env`. TLS is turned on automatically for `*.neon.tech` hosts, and a `channel_binding` option in the string is ignored safely.

Tips: use a Neon **branch** for development so you never touch production data (copy that branch's strings into your local `.env`). A free-tier database can pause when idle, so the first request after a quiet period may take a moment; the server waits up to 15 seconds for it to wake.

If you ever deploy to serverless functions or edge runtimes instead of a normal Node server, swap `pg` for Neon's serverless driver. This server is a long-running Node process, where `pg` is the right choice.

Any other PostgreSQL 13+ also works: set `DATABASE_URL` only (and `DATABASE_SSL=true` if it needs TLS). `docker-compose.yml` gives you a local one.

## Run it locally

```bash
# 1. Server
cd server
cp .env.example .env      # fill in the two Neon strings and JWT_SECRET (instructions inside)
npm install
npm run dev               # http://localhost:4000, applies migrations on start

# 2. Front end (second terminal, project root)
npm install
npm run dev               # http://localhost:5173, /api is proxied to :4000
```

`npm run migrate` applies migrations on its own. Add schema changes as `migrations/002_*.sql` (each file runs once, in name order, and is safe to run from several instances at once).

## API

All routes are under `/api`. Everything except `auth/*` and `health` needs the session cookie.

| Method | Path | What it does |
|---|---|---|
| POST | `/auth/signup`, `/auth/login` | `{ email, password }` (8+ chars). Sets the session cookie |
| POST | `/auth/logout` | Clears the cookie |
| GET | `/auth/me` | Current user |
| GET | `/workspace` | Whole workspace in the shape the React app uses (also creates any due monthly copies of repeating transactions) |
| DELETE | `/workspace` | Wipe this account's data and restart setup |
| PUT | `/profile` | Partial update: `name, income, essentials, commitments, savings` |
| POST | `/onboarding` | First-run setup |
| POST / DELETE | `/transactions`, `/transactions/:id` | |
| PUT / DELETE | `/budgets/:category` | One budget per category |
| POST / DELETE | `/subscriptions`, `/subscriptions/:id` | |
| POST / PATCH / DELETE | `/goals`, `/goals/:id` | PATCH takes `{ saved }` or `{ add }` |
| POST | `/scenarios` | |
| POST | `/currency/convert` | `{ to, factor }`: converts every stored amount atomically |
| GET / POST | `/ai/health`, `/ai/analyze` | AI proxy: Groq then Gemini (503 until `GROQ_API_KEY` or `GEMINI_API_KEY` is set) |

Money is stored as `numeric(16,2)`, dates as `date`. Every query is scoped by the session's user id.

## Security notes

- Passwords: bcrypt (cost 12). Login answers the same for unknown email and wrong password.
- Session: JWT in an `httpOnly`, `SameSite=Lax` cookie (`Secure` in production), 7 days. Logout clears the cookie but a stolen token stays valid until it expires; add a sessions table if you need server-side revocation.
- Writes from a browser Origin that is not in `CLIENT_ORIGIN` are rejected. Auth routes are rate limited (20 per 15 min per IP), AI to 8 per minute per user.
- Inputs are validated with zod; all SQL is parameterised; request bodies are capped at 100 KB.
- AI keys stay on the server. The AI payload contains no transaction descriptions.
- Behind a proxy or load balancer, set `NODE_ENV=production` (enables `trust proxy` and secure cookies) and serve over HTTPS.

## Deploying (Render)

The root `render.yaml` describes one Render web service that builds the React app and runs this server, which serves `dist/` and `/api` from one address (so login cookies work with no extra setup).

- Build: `npm ci && npm run build && cd server && npm ci`; start: `cd server && npm start`; health check: `/api/live` (does not touch the database, so it never wakes a paused Neon database).
- Required variables: `DATABASE_URL` (Neon pooled), `DATABASE_URL_UNPOOLED` (Neon direct), `JWT_SECRET` (generated by the Blueprint), `NODE_ENV=production`.
- Optional: `GROQ_API_KEY` and/or `GEMINI_API_KEY` (AI page; Groq is tried first, then Gemini), and `CLIENT_ORIGIN` (your site URL; same-origin requests are already accepted without it).
- Migrations run automatically on each start. Render supplies `PORT`.

Not included yet: email verification, password reset, account deletion.

## AI providers

`/api/ai/analyze` tries the providers listed in `AI_PROVIDERS` (default `groq,gemini`) in order. A provider is used only if its key is set. A provider that is busy (429/5xx), times out, rejects the key or returns an unreadable answer is skipped and the next one answers; each model gets two tries when it reports being busy. Render's logs show which one answered (`AI answered by groq (...) in 900ms`).

- **Groq** (OpenAI-compatible, free plan): `GROQ_API_KEY`, `GROQ_MODEL` (default `openai/gpt-oss-120b`), optional `GROQ_FALLBACK_MODEL`.
- **Gemini**: `GEMINI_API_KEY`, `GEMINI_MODEL` (default `gemini-3.8-flash`), optional `GEMINI_FALLBACK_MODEL`.
- Model names change over time. A log line like `groq 404 (model)` or `gemini 404 (model)` means the name was retired; set the matching `*_MODEL` variable to a current one.
